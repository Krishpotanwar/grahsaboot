# R3 research: imagery providers, data access, quotas, licences

Date of research and access date for every source: **2026-10-05**. Worker: Sonnet (R3 imagery domain). Scope: verify every provider/data claim in `ARCHITECTURE_V2.md`, `research/2026-10-05-provider-audit.md` and `TRD.md`; hunt counter-options; answer the key question (simplest, legally clean, ₹0-start, scalable imagery path).

Conventions. **[F]** = fact read from a primary source today. **[M]** = measured by me today with live requests from this VM (reproducible commands in Appendix A). **[I]** = inference, flagged. Currency: 1 EUR = 108.37 INR, 1 USD = 96.31 INR (open.er-api.com mid rate, 2026-10-04 00:02 UTC; web forecasts say roughly 110, so treat INR as +/-2%). EUR prices exclude VAT/GST, as the sellers state.

## 0. Bottom line (read this first)

1. **Every provider claim in the three docs checks out or is a defensible paraphrase, with five corrections** that matter (section 2): (a) the *request* meter, not the PU meter, is the binding free-tier limit, about 100x earlier; (b) the P13 sentence about "credential-protecting authentication service" is not in the FAQ today; (c) the openEO billing model changed on 2026-03-02 (failed jobs billed, about 25% fewer credits per job); (d) Sentinel-2 now has three operating satellites until 2026-12-31, and 2A paused imaging 13 Jan - 8 Mar 2026; (e) the Earth Search STAC now has three Sentinel-2 L2A collections and the new `sentinel-2-c1-l2a` is still incomplete for India.
2. **The docs missed a better launch path.** Sentinel-2 true-colour (`TCI.tif`) and scene-classification (`SCL.tif`) Cloud-Optimized GeoTIFFs sit in public AWS buckets with `Access-Control-Allow-Origin: *`, no credentials, no requester-pays, and the STAC search endpoints (Earth Search and CDSE) also send CORS `*`. A browser can search, read a 1 km2 window per date, count cloud pixels from `SCL.tif`, and draw the before/after and timeline with **zero imagery server, zero quota, zero keys**. I measured it end to end (section 3, CP1).
3. **Decision recommended:** launch on browser-direct COG reads (no SH meter). Keep CDSE Sentinel Hub Process as the documented *upgrade* for server-rendered, provider-attested evidence. Apply for CREODIAS "Credits for value creators" on day 1 (free, 30-day decision) as insurance. This is a processing-placement change that ARCHITECTURE_V2 section 3 explicitly reserved for the owner, so it needs an owner decision.
4. **Paid scaling is cheap if you ever need the Sentinel Hub meter:** CREODIAS Sentinel Hub "Basic" = EUR 999/year (about ₹1.08 lakh, ₹9,022/month) for 700,000 requests and 70,000 PU per month, versus 10,000/10,000 free. "Exploration" (EUR 300/year) is labelled non-commercial and is not usable for this product.
5. **Do not render dated imagery in the frontend through Sentinel Hub OGC/WMTS.** It works technically but burns about 1 request per 256 px tile (so about 500-800 map views a month on the free tier, shared by all users) and puts the instance ID (the only OGC credential) in every browser.
6. **Free higher-resolution imagery that is also commercially usable over India does not exist in a form this product can use at launch.** Bhoonidhi gives free 5.8 m LISS-IV/LISS-III to registered users under an EULA that allows commercial services but forbids commercial redistribution of original data; sub-5 m is priced. Maxar/Vantor open data and NICFI are non-commercial. CCM VHR is Europe-only. Satellogic is a sample set.

## 3. Counter-proposals (what the docs missed)

### CP1. Browser-direct Sentinel-2 COG reads (recommended launch path)

- **What:** the front end calls a public STAC search (Earth Search `POST /v1/search`, or CDSE `GET stac.dataspace.copernicus.eu/v1/search`; both CORS `*`, measured) for dated scenes over the site, then reads a **window** from `TCI.tif` (8-bit true colour, 10 m, 3 bands) and `SCL.tif` (20 m class map) with geotiff.js, draws it to a canvas, and counts cloud/shadow/nodata classes inside the polygon from the SCL window. Optionally uploads the canvas PNG plus a JSON of `{collection, item id, datetime, s2:processing_baseline, asset hrefs, bbox, window}` to Supabase Storage.
- **Licence:** Sentinel data under the EU Legal Notice (free, full, open, attribution). Earth Search and the AWS buckets give no formal service guarantee ("no guaranteed service"); I found no separate prohibition on commercial use in the README or registry text, but Element84's own terms of service were not located (**UNVERIFIABLE**).
- **Measured cost (Appendix A):**
  - 1 km2 `TCI.tif` window: 100x100 px, 9-14 HTTP range requests, **2.24 MB** (one 1024x1024 internal tile), **514 ms CPU** in Node including cold start, about 5-7 s wall from this VM.
  - Same area `SCL.tif`: 50x50 px, **22 KB**, 49 ms CPU. In the test window SCL counts were class 4 (vegetation) 1,916 and class 5 (not vegetated) 584, so quality stats are computable in-browser with no server.
  - `search` for one point, 9 months: 1.7 s, 70 items. The response was 1.3 MB without a `fields` filter; use `fields.include`.
- **₹0 cost:** hosting is static Cloudflare Pages (already chosen). No keys, no quota meter, no queue, no work_items/attempts/reservations tables for imagery. At scale the cost is AWS's (Open Data sponsorship) and the user's bandwidth: about 2.2 MB per date per MGRS tile block; a 12-date before/after/timeline is about 27 MB for a one-tile site, about 80 MB for a 10 km road crossing three blocks **[I]**. Use overview levels for thumbnails and full resolution only on demand.
- **Scale when needed:** the same read runs on a server unchanged (Supabase Edge or any worker; CPU 0.5 s per cold 1 km2 frame measured in Node, Deno untested; Supabase Edge limit is 2 s CPU per request per ARCHITECTURE_V2). Inputs are immutable public objects, so a server re-render is reproducible and can be hashed.
- **Why it beats SH Process at launch:** no meter shared by all users (SH free = 10,000 requests/month for the entire product), no OAuth secret, no tar parsing, scene identity is the STAC item ID (no `userdata` mapping puzzle), baseline read directly from the item.
- **Why it loses to SH Process:** SH mosaics and reprojects across MGRS tiles and UTM zones server-side and returns small PNGs (about 30 KB); in the browser you must mosaic up to four tiles and reproject yourself (India spans UTM 42-47). Provider-side attestation of a render, background processing with the browser closed, and bandwidth on mobile all favour SH.
- **Fallbacks for the same pattern:** Planetary Computer (`sentinel-2-l2a`, `visual` + `SCL`, SAS tokens, CORS on STAC), CDSE STAC (no CORS issue, but assets are `s3://eodata` so not browser-readable; use for catalogue and baseline only).

### CP2. Using CDSE public STAC as a free catalogue and baseline source

`https://stac.dataspace.copernicus.eu/v1` needs no token, sends CORS `*`, and each Sentinel-2 L2A item carries `processing:version` (for example `05.13`), full ESA product name (e.g. `S2A_MSIL2A_20261002T053241_N0513_R105_T43RGM_20261002T101803`) and `processing:datetime`. **[M]** Its timestamp is the product start (05:32:41) while Earth Search and SH tile sensing times differ by minutes, so match with a window under 50 minutes. Use it to replace SH Catalog calls (saves requests), to hold the exact product ID in the evidence record, and as a baseline cross-check. Stac transfer counts against the CDSE 12 TB/30-day fair-use bucket, not SH requests.

### CP3. If SH is kept: how to stay inside 10,000 requests

(a) Catalog `distinct: date` or CDSE STAC for date discovery; (b) one Statistical request per section with `aggregationInterval P1D`; (c) one Process call per accepted frame returning PNG + `userdata` in one tar; (d) cache by hash of (bbox, window, evalscript); (e) a Cloudflare/Supabase cache in front so that identical frames for different users cost one request. [I] This gives about 70 requests per analysis, about 140 analyses a month free.

### CP4. Sentinel Hub OGC/WMTS from the browser (the question asked)

- **Feasible:** `https://sh.dataspace.copernicus.eu/ogc/wmts/<INSTANCE_ID>?...&TIME=2026-10-02/2026-10-02&LAYER=...`; instance configured in the dashboard Configuration Utility; WMTS `TIME` takes `from/to` and a single value is deprecated ([WMTS](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/OGC/WMTS.html), [OGC overview](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/OGC.html)).
- **Credential exposure:** the instance ID "is used to authenticate your OGC requests", so it is public in page source. I found no documented per-origin restriction for instances (UNVERIFIABLE). The SPA OAuth client option has origin allow-listing but ships a secret to browsers and carries an explicit risk warning.
- **Quota:** each 256x256 tile is a request and about 0.25 PU (area 65,536 / 262,144) per the PU rule **[I]**, so 10,000 requests per month is about 10,000 tiles, at about 12-20 tiles per map view roughly **500-800 views per month for all users combined**. One visitor panning can exhaust the month.
- **Other gaps:** `mostRecent` mosaic of that day only (same stitching caveat as Process), no per-scene identity, no quality statistics unless you add Statistical calls, no durable evidence unless you also screenshot tiles.
- **Verdict:** reject for frontend rendering. Possible for an internal analyst tool behind a login.

### CP5. NASA GIBS per-date XYZ tiles (HLS S30, free, no key)

`HLS_S30_Nadir_BRDF_Adjusted_Reflectance` (Sentinel-2-based, 30 m) is a per-date WMTS layer (`.../default/{Time}/GoogleMapsCompatible_Level12/{z}/{y}/{x}.png`), time dimension to 2026-10-02, no credentials, CORS `*`. **[M]** a Delhi z12 tile for 2026-10-02 rendered with the JLN stadium and street grid visible; responses carry `cache-control: no-store` (weak browser caching). Max zoom is level 12 (about 34 m/px at Delhi's latitude); z13 returned HTTP 400. NASA licence page states a free and open policy. Resolution is 3x coarser than Sentinel-2 native, so roads under about 60 m and buildings are not interpretable. Useful only as a free context layer or emergency fallback; fails the "building/road evidence" requirement.

## 4. Best recommendation (decisive)

**Launch with browser-direct reads of Sentinel-2 L2A COGs located through STAC.** Concretely:

1. Search: Earth Search `sentinel-2-l2a` (complete archive from 2017 over Delhi; fields filter `id, datetime, eo:cloud_cover, s2:processing_baseline, s2:nodata_pixel_percentage`). Optionally cross-check baseline against CDSE STAC `processing:version`.
2. Quality per date: read the `SCL.tif` window (about 22 KB per 1 km2), count classes inside the confirmed polygon, with the denominator and class policy already specified in ARCHITECTURE_V2 section 5.3 (the policy text can stay as written).
3. Image per date: read the `TCI.tif` window, draw to canvas, store `{collection, id, baseline, bbox, window, hrefs}` with the PNG in Supabase private storage if the user saves evidence. TCI is Sentinel's own fixed true-colour rendering, so every frame uses the same stretch.
4. Provenance: STAC item ID plus baseline, not a `userdata` mapping.
5. Attribution on every export: `Contains modified Copernicus Sentinel data 2026`.
6. Day 1 actions: apply for Credits for value creators; email NRSC for a written ruling on LISS-IV crop display; keep one CDSE account (never one per user).
7. Do not build the SH Catalog/Statistical/Process integration until a trigger fires: government/audit users need provider-attested stored renders, or measured mobile bandwidth is the main drop-off, or road corridors across tile and zone boundaries make client-side mosaicking painful.

This removes the shared 10,000-request meter, OAuth secrets, tar parsing, the scene-identity puzzle, the reservation/retry accounting for imagery, and most of the cron-scheduled worker, while keeping the evidence promise (dated real acquisitions, honest cloud gaps, notes, export). It leaves D6 (free/open imagery only) and the 1-month, ₹0 constraints intact. It changes D9 only in who runs the processing step (the user's browser rather than a provider API), so the owner must approve.

### Strongest argument against

A tampered or inconsistent browser is an unreliable evidence factory. The product's value proposition is evidence people may rely on in disputes with contractors or officials. With CP1, the PNG that lands in storage was produced on an arbitrary device, cannot be proven by the server, and the product depends on two best-effort community services (Earth Search with "no guaranteed service", and a bucket naming that has already changed once, plus a new `c1` collection that is still incomplete) with no SLA and no one to call. The 80 MB timeline on a 4G phone in a district town may simply fail, and the browser cannot keep working with the tab closed. Sentinel Hub gives one stitched, provider-rendered, metadata-carrying frame for 0.04 PU that works identically on every device, and a published price (EUR 999 a year buys 700,000 requests). If the first paying users are government or legal auditors, SH (or a server-side re-render from the same COGs) is the right default and CP1 becomes only a preview tier. I rate this risk real but deferrable: demand is unvalidated (D2/D3), and a server re-render from identical immutable COG inputs is a small addition once evidence-grade output is demanded.

## Round 2 cross-examination (browser-direct COG recommendation)

Date 2026-10-05. Everything marked **[M]** was measured today from this VM with scripts using geotiff.js 2.x on Node 22 and Deno 2.9.6; the timings are single cold runs from one datacentre, not benchmarks. Scene used unless stated: `S2A_43RFM_20261002_0_L2A` (`TCI.tif` 10980x10980, 1024-px blocks, 5 overview levels; `SCL.tif` 5490x5490, 512-px blocks). **Correction to my first pass:** CP1 said a 10 km road is "about 80 MB for a 12-date timeline across three blocks". The measured corridor-aware figure is lower (question 3): mean 57 MB, 95th percentile 88 MB, worst case 123 MB.

### Q1. Attestation: can the pixels be re-derived and verified?

**Verdict: yes while the source object is unchanged, with a pixel hash as the primary key, not the ETag. A server spot-check on Supabase Edge is feasible for a 1 km2 window. Nothing here proves a client did not forge a manifest; only a server re-derive does.**

Facts about the objects **[M]**:
- **No object versioning.** Anonymous `ListObjectVersions` is allowed on `sentinel-cogs`; every sampled key (2018, 2022, 2026) shows exactly one version with `VersionId` = `null`, no delete markers. So an object can be overwritten with no history. The `e84-earth-search-sentinel-data` bucket (c1) refuses version listing (AccessDenied), so its history is unknown.
- **Objects do get rewritten.** The 2018-12-31 scene (`S2A_43RFM_20181231_0_L2A`, baseline 02.11) has `Last-Modified: 2020-10-04`, while its STAC item was created 2022-11-03 and updated 2022-11-08. The 2022-12-30 and 2026-10-02 objects were written the day of acquisition. So rewriting of historical objects has happened at least once.
- **ETag is not a pixel identity.** The same scenes exist in both collections. Windows read from `sentinel-2-l2a` and `sentinel-2-c1-l2a` for `2025-12-29 S2B` and `2022-12-30 S2A` were **bit-identical** (0 differing samples of 30,000 TCI and 2,500 SCL; same SHA-256), yet the files differ (97,498,786 vs 97,327,141 bytes, different ETags) because they were re-encoded. So an ETag change does not mean pixels changed, and a matching ETag is only a fast path.
- **Whole-object checksums exist only on new objects.** HEAD with `x-amz-checksum-mode: ENABLED` returns `x-amz-checksum-crc64nvme` (type `FULL_OBJECT`) for the 2026 object and nothing for the 2022 one.
- **Decoding is deterministic.** Re-reading the same 100x100 window gave identical bytes; **Node 22 and Deno 2.9 produced the same SHA-256 (prefix `28770425b3051602`)**.

**Manifest to store (all immutable facts):** `collection`, STAC `id`, asset href, `ETag`, `Last-Modified`, CRC64NVME if present, `s2:processing_baseline`, pyramid level, pixel window `[x0,y0,x1,y1]`, CRS (EPSG) and affine transform of that level, recipe version (`tci-window-v1`: no resampling, uint8 interleaved RGB), and **SHA-256 of the raw decoded RGB byte array** (never of a PNG: canvas/PNG encoders differ between browsers). For quality stats store the same for `SCL.tif` plus the polygon mask recipe and the class counts.

**Third-party re-derive:** anyone can run `HEAD`, read the same window, hash the raw array and compare. That verifies provenance as long as the object is unchanged or at least pixel-identical. If AWS later replaces a scene (reprocessing), the hash will not match and nobody can re-derive it; the PNG we copied into private storage is then the only evidence copy (this is why ARCHITECTURE_V2's "copy bytes before publishing" rule stays). Wherever the manifest says "ETag differs, pixel hash matches", accept it.

**Server spot-check feasibility (1 km2 `TCI.tif` window, Deno 2.9, `npm:geotiff@2`) [M]:** 0.30-0.34 s CPU (user) plus 0.04-0.05 s system, peak RSS 94-98 MB, wall 3.3-4.4 s (network dominated), 2.24 MB downloaded. That is within the 2 s CPU / 256 MB / 150 s limits quoted in ARCHITECTURE_V2. Not tested inside the real Supabase edge-runtime (**UNVERIFIED**; it is Deno-based but is not identical to desktop Deno). **[I]** A 10 km corridor touches up to four 2.2-2.7 MB blocks (worst 10.2 MB, question 3) so about 1.2 s CPU: verify per 2 km section, not the whole corridor in one call. `SCL.tif` verification is 22 KB and about 50 ms.

**Sampling policy [I]:** verify a random 5-10% of saved frames plus every frame in an "audit-grade" report; mismatch marks the frame unverified. It needs no new component beyond one Edge function. It cannot make a malicious client honest for unsampled frames; say so in the report ("client-derived, server-verified on sample").

### Q2. Scale and abuse: AWS terms, 10k-100k users, proxying

- **Requester pays:** no. Anonymous `GET` of `sentinel-cogs` and `e84-earth-search-sentinel-data` works (`206`, CORS `*`). The Landsat bucket (`usgs-landsat`) is the requester-pays one **[M]**.
- **Terms [F]:** the registry says datasets are "provided and maintained by a variety of third parties under a variety of licenses" ([About](https://registry.opendata.aws/about/)); Sentinel-2 COGs are managed by Element84. I found **no rate-limit or fair-use clause** in the dataset page, the sponsorship page or the onboarding handbook. The **AWS Open Data Sponsorship Program covers storage and data transfer for two years, renewable "under agreement from all parties"**; its terms (s1.5) say participation "will automatically terminate" after 2 years unless extended ([program terms](https://aws.amazon.com/opendata/open-data-sponsorship-program/terms/), [handbook](https://assets.opendata.aws/aws-onboarding-handbook-for-data-providers.pdf)). The real risk is therefore a lapse or policy change, not a published limit. Whether this particular bucket is in the sponsorship program, and its current term, are **UNVERIFIABLE** from public pages. S3's own per-prefix request ceilings were not fetched.
- **Volume model [I, from measurements below]:** a site timeline is about 34 MB (12 dates x 2.83 MB mean), a 10 km road about 57 MB. At 10k analyses/month that is 0.34-0.57 TB; at 100k users about 3.4-5.7 TB/month, roughly 17 million range GETs (about 14 per frame). That is ordinary for S3, and AWS, not us, pays it while sponsored. We pay nothing but our own static hosting.
- **Do not proxy COG bytes through Cloudflare.** Workers Free is 100,000 requests/day and 10 ms CPU; with about 14 range requests per frame that is about 7,000 frames a day. The Free CDN caches objects up to 512 MB (our TCI files are 97-370 MB) and serves range requests "from complete or partial cached files", but caching whole 270 MB objects to serve 2 MB windows is wasteful, and Cloudflare's free-plan terms for heavy non-HTML traffic were not checked (**UNVERIFIED**) ([cache limits](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
- **What to cache instead:** (1) in the browser, Cache Storage keyed by `href + ETag + window`; (2) later, only if measured duplication justifies it, a shared cache of *derived frames* in Cloudflare R2. R2 free tier: 10 GB-month storage, 1 million Class A and 10 million Class B operations per month, no egress charge ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)). (3) Only if Earth Search throttles, a GET-based STAC search cache via the Workers Cache API. None of these is needed on day 1.

### Q5. SCL per-AOI quality in the browser versus the Statistical API

**Verdict: accurate to about 1 percentage point of the polygon's class fractions in my tests, with no loss in the data itself; remaining differences are tile selection and the Statistical API's own rasterisation rule, which I could not test without an account.**

- **Source fidelity [M]:** the whole-scene class shares of the `SCL.tif` COG (read in full, 30 M pixels) equal the scene percentages published in the STAC item (`s2:vegetation_percentage`, `s2:cloud_shadow_percentage`, `s2:medium_proba_clouds_percentage`, and so on) to 0.01 pp on three scenes with 50%, 86% and 100% cloud (e.g. 2025-08-21: cloud-medium 21.18 vs 21.18, shadow 13.58 vs 13.58, vegetation 27.96 vs 27.96). Those STAC numbers come from the ESA product metadata, so the COG conversion preserved the classes. This is an aggregate match, not a per-pixel comparison with ESA's JP2.
- **Do not compute stats from overviews [M]:** SCL overview pixels equal the nearest top-left source pixel 97% of the time and keep valid class codes (no averaged codes), and class shares were within 0.3 pp, so overviews are acceptable for thumbnails and gating but statistics must use the native 20 m level.
- **Polygon rasterisation error [M]:** in the 50%-cloud scene, against a 2 m super-sampled truth for 150-300 random corridors: pixel-centre rule at 20 m, mean error 0.04 pp (10 km x 200 m), 0.08 pp (2 km section), p95 0.10-0.24, max 0.26-1.17; "any corner touches" rule at 20 m is worse (mean 0.17-0.43, max 2.7 pp); **centre rule on a 10 m grid with the 20 m class map nearest-upsampled** (what Sentinel Hub does at a 10 m request) mean 0.01-0.02, p95 0.03-0.08, max 0.6. Use the 10 m centre rule. The test class set was nodata, defective, shadow, cast shadow, cloud medium/high, cirrus and snow.
- **What the browser cannot match:** (a) Sentinel Hub mosaics all tiles of a day, so a polygon straddling two tiles gets pixels from both; the browser reads one item and must flag "not fully covered" (Q3: 99-100% fully covered on 8 of 10 corridors); (b) SH's exact polygon rasteriser and any `dataMask` convention are undocumented in what I read (**UNVERIFIABLE** without credentials); the error is bounded by the 1 pp seen above and is far smaller than SCL's own documented misclassification (SentiWiki lists low-cloud, fog and shadow errors).
- **Required test before release:** run both paths on 20 real corridors and compare class counts; this needs a CDSE account.

### Q6. Decisive comparison at 10k analyses/month

Workload assumption (ARCHITECTURE_V2): 12 dates; site = 1 section, road = 5 sections.

| | Browser-direct COG (+ server verify) | CDSE Sentinel Hub paid |
|---|---|---|
| Requests/month | none to SH; about 17 M range GETs to AWS (browser), plus 10k searches | 70 per analysis (batched Catalog/Statistical/Process) = **700,000**; or 245 per analysis = 2.45 M |
| Plan that fits | none | 700k = **exactly the Basic cap** (EUR 999, 700,000 requests) with zero headroom; practical choice **Enterprise-S** EUR 5,000/yr (800,000 requests, 300/min as printed) = **Rs 5.42 lakh/yr**; the 245-call design needs **Enterprise-L** EUR 10,000/yr (10 M requests) = **Rs 10.84 lakh/yr** |
| Cost per analysis | Rs 0 to us; the user spends about Rs 0.2-0.4 of mobile data | about Rs 4.5-9 |
| Failure mode | AWS sponsorship lapse; slow mobile first view; client-forged evidence unless server-verified | quota meter exhausted; plan price changes; one shared account and OAuth secret |
| Evidence quality | pixel-hash manifests, server sample verify; no cross-orbit mosaic | provider-rendered stitched frame, `userdata` scene IDs |

(EUR 1 = Rs 108.37; plan prices from the CREODIAS table in section 2.4; VAT excluded.)

**Decision: browser-direct wins at 10k analyses/month, by about Rs 5-11 lakh a year, and the server-side COG verifier (Q1) is the evidence tier, not Sentinel Hub.** At that volume the product has demand evidence and can afford a small always-on worker to re-derive and store frames from the same public COGs (measured 0.3 s CPU per 1 km2 frame); Sentinel Hub buys only cross-orbit stitching and provider attestation, which this product already treats as honest gaps and sampled verification. **Strongest remaining case for SH, stated fairly:** if the paying users are auditors or lawyers who will not accept any client-derived evidence, and if more than about 20% of real corridors sit in partial-orbit overlaps like Kutch and Nagpur (2 of my 10), then SH Process (or a server renderer) becomes the default and browser-direct becomes preview only. **Flip triggers to monitor:** p95 time-to-first-frame above 15 s on mid-range Android; AWS 403/503 or sponsorship notice; partial-date share above 20% of dates; any customer requiring provider-attested frames. Until then do not build the SH integration.

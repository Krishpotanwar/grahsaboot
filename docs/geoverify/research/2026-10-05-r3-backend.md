# R3 backend, hosting, storage, auth, queues, scaling, cost

Date: 2026-10-05 (all pages accessed this date). Scope: hosting/backend claims in `ARCHITECTURE_V2.md` (R2), `research/2026-10-05-provider-audit.md` (P15-P21) and `TRD.md`. Fact = read from the cited page today. Inference = my reasoning, labelled. Nothing here was run or deployed. Fetch tool returns model-summarised page text, so any number that drives a decision is flagged where I could not see the primary table myself.

## 0. Verdict in five lines

1. The docs' hosting facts are almost all CONFIRMED. Two are stale or incomplete: **Cloudflare now says "Start new projects with Workers"** (Pages is not end-of-life but is no longer the recommended target), and the Edge limits omit that the **paid wall limit is 400 s**.
2. The docs have **no DPDP Act/Rules analysis and no data-region decision**. Both matter now: Rules notified 13 Nov 2025, core duties bite 13 May 2027, and Rule 6's one-year log retention collides with Supabase's 1-day (Free) / 7-day (Pro) log retention.
3. Pick: **Supabase (Mumbai, ap-south-1) for everything stateful + Cloudflare Worker with static assets for the frontend**. Use **pgmq** as the dispatch queue inside the same Postgres. Do **not** add R2, Cloudflare Queues/Workflows/D1, Inngest, Trigger.dev, Neon, Upstash at launch.
4. Free tier breaks at roughly **120 analyses/month on egress** and **300/month on storage** (derived, section 4). At ~1,000/month the bill is **$25 (about ₹2,400)**; at ~10,000/month about **$41-56 (₹3,900-5,400)**, before 18% GST.
5. Strongest case against: an all-Cloudflare build (Workflows + Queues + D1 + R2) is cheaper (about $5.5/month at 10,000), pauses nothing, has free 7-day restore, and Workflows are literally "durable jobs + retries". It loses only because it has no managed auth, no PostGIS, no RLS. That is a real trade, not a slam dunk (section 7).

## 2. Counter-proposals checked

Format: what / licence-commercial / cost at ₹0 and scale / verdict vs current choice.

**C1. Supabase Queues (pgmq) instead of hand-rolled claims.**
- What: Postgres-native queue on the pgmq extension; "guaranteed and exactly-once delivery within customizable visibility windows"; archive for audit; RLS-controlled; **not exposed on the Data API by default**. Functions: `send`, `read` (with visibility timeout), `archive`, `set_vt`; read count (`read_ct`) available. https://supabase.com/docs/guides/queues , https://supabase.com/docs/guides/queues/quickstart , https://supabase.com/docs/guides/database/extensions/pgmq . The older launch blog calls it Public Alpha (Dec 2024); the docs today say GA.
- Licence/cost: PostgreSQL licence (Tembo, per Supabase blog); no separate charge; lives in your DB. The docs I read state **no Free-plan restriction** but also do not explicitly affirm Free availability: UNVERIFIED until you enable it on a Free project.
- Verdict: **adopt for dispatch only.** It replaces the hand-written lease/claim/redelivery SQL (visibility timeout = lease; `read_ct` = attempt count; `set_vt` = backoff). It does **not** remove `work_items` (user-visible phase/state), the attempts ledger, the fencing token or "one provider call in flight application-wide" (needs a lease row, not an advisory lock, because pooled connections make session locks unreliable; inference). Enqueue inside the same transaction as the `work_items` insert, so there is no dual-write gap. If Free blocks it, fall back to `FOR UPDATE SKIP LOCKED` with a `lease_until` column: same semantics, about 20 lines. Close call, so do not let it block week 1.

**C2. Cloudflare R2 for evidence images vs Supabase Storage.**
- Fact: R2 Standard $0.015/GB-month; Free 10 GB-month, 1 M Class A, 10 M Class B ops/month; **egress free**; presigned URLs for GET/PUT/DELETE up to 7 days but **only on the S3 domain, not custom domains**. https://developers.cloudflare.com/r2/pricing/ , https://developers.cloudflare.com/r2/api/s3/presigned-urls/
- Compare storage price: Supabase Pro overage is $0.0213/GB vs R2 $0.015/GB: a 30% discount on a tiny number. The real differences are the 10x free capacity (10 GB vs 1 GB) and zero egress.
- Derived break-even (section 4): at 10,000 analyses/month, R2 saves about **$15/month** (egress overage $15.75 minus R2 storage $0.35). Below about 5,900 analyses/month (the Pro 250 GB egress quota) it saves nothing once you are on Pro.
- Cost: adds a second credential system to Edge Functions (S3 SigV4 signing), a second purge target (orphans across two stores), and a second place for DPDP erasure. It is not covered by Supabase RLS, so every signed URL must be minted after an ownership check in code.
- Verdict: **not at launch.** Add it only if egress overage appears or the ₹0 stretch past about 300 analyses/month on Free is wanted (section 4 "₹0 stretch").

**C3. Cloudflare Queues / Workflows / Durable Objects / D1 / Cron as the orchestrator.** All are available on Workers Free:
- Queues: 10,000 operations/day, 24 h retention (Paid: 1 M ops/month then $0.40/M, 4-14 d retention); a message costs write+read+delete = 3 ops. https://developers.cloudflare.com/queues/platform/pricing/
- Workflows: Free 100 concurrent running instances, 1,024 steps, **10 ms CPU per step**, 100,000 executions/day, 3-day state retention; Paid 30 s CPU/step default (up to 5 min), 10,000 steps, 30-day retention; wall time per step unlimited; sleep up to 365 days; waiting instances do not count to concurrency; 1 MiB per payload/step result. https://developers.cloudflare.com/workflows/reference/limits/
- Durable Objects on Free: SQLite backend only; 100,000 req/day, 13,000 GB-s/day, 5 GB. https://developers.cloudflare.com/durable-objects/platform/pricing/
- D1: Free 5 M rows read/day, 100,000 rows written/day, 5 GB; Time Travel 7 days Free / 30 days Paid at no charge. https://developers.cloudflare.com/d1/platform/pricing/ , https://developers.cloudflare.com/d1/reference/time-travel/
- Workers Cron: Free up to 5 triggers, CPU 10 ms Free; minimum interval is 1 minute (the page shows `* * * * *`); changes take up to 15 min to propagate. https://developers.cloudflare.com/workers/configuration/cron-triggers/
- Fit: Workflows are the best native fit for "many sequential provider calls, each retried, state persisted, browser closed". Steps here are mostly network wait (excluded from CPU), so the 10 ms Free CPU limit is plausible but **must be measured** (JSON parse of Statistical responses, token handling). Missing pieces: **no managed auth, no PostGIS, no RLS, no Postgres**.
- Verdict: **the serious alternative.** Rejected for launch only on the auth/PostGIS/RLS gap; see section 7.

**C4. Vercel.** Hobby plan "restricts users to non-commercial, personal use only" (fair-use guidelines, cited on the Hobby page); Pro seats $20/user/month. https://vercel.com/docs/plans/hobby . A commercial product cannot sit on Hobby. **Excluded.**

**C5. Neon.** Free: 1 GB/project (20 GB account), 100 CU-hours/project, scale-to-zero after 5 min (cannot disable on Free), 60,000 MAU for Neon Auth; Launch $0.35/GB-month, $0.106/CU-hour, no minimum. https://neon.com/pricing . Regions (Mumbai/Singapore) not stated on the fetched page: UNVERIFIED. Gives Postgres only; you would still need storage, a queue, cron and an Edge runtime. **Loses** to Supabase on component count.

**C6. Upstash.** Redis Free 256 MB / 500K commands/month; pay-as-you-go $0.2 per 100K commands. https://upstash.com/pricing . QStash (the relevant durable-HTTP-queue product) terms were **not on the page fetched**: UNVERIFIABLE. Redis is explicitly out per ARCH and DESIGN. **Excluded.**

**C7. Inngest.** Free: 50k executions/month, 5 concurrent steps, 3 workers; Pro from $99/month (1 M executions). An "execution" counts per function run plus each step. https://www.inngest.com/pricing . At about 43 steps/analysis (section 4 profile) Free covers about 1,100 analyses/month, then jumps to $99. You still need a host for the functions, a DB and storage. **Loses**: extra vendor and a price cliff.

**C8. Trigger.dev.** Free: $5 monthly credit, 20 concurrent runs, 1-day log retention; Hobby $10, Pro $50; Micro machine $0.0000169/s plus $0.000025 per run. https://trigger.dev/pricing . Billed on wall-clock, so waiting on provider calls costs money (inference, about 130 s/analysis x $0.0000169 = $0.0022, small). Still needs DB + storage elsewhere. **Loses** on component count, not on price.

**C9. Single platform: all-Cloudflare vs all-Supabase.**
- All-Supabase is not possible for the frontend: Supabase has no static-site hosting product. (I recall Storage serving HTML as text/plain; not verified today, so do not rely on it.) The minimum is therefore **two vendors**: Supabase + Cloudflare.
- All-Cloudflare is one vendor but you build auth. Use of a library (for example Better Auth) with Google OAuth over D1 is feasible but is security-critical code and session custody you now own; D1 has no spatial functions, so polygon validation, areas and road buffering move to JS (Turf-style), which is less rigorous than PostGIS geography functions (inference). Authorisation moves from RLS to application code on every route.
- Verdict: Supabase + Cloudflare = 2 vendors and almost no custom security code. All-Cloudflare = 1 vendor and custom auth/geometry. For a team of five students with no spare security budget, Supabase wins the "fewest moving parts that are *your* parts" test. Vendor count is not the right metric; owned-code surface is.

## 3. (a) The ₹0 launch topology (fewest moving parts)

```
Browser (React/Vite/Leaflet)
   |  static files                      |  Supabase JS (Auth, PostgREST reads, signed URLs)
   v                                    v
Cloudflare Worker (static assets, SPA)    Supabase project, region ap-south-1 (Mumbai) [verify Free allows]
  + scheduled(): daily ping (optional)     - Auth: Google only (openid/email/profile)
                                           - Postgres: PostGIS in `extensions`; analyses, observations,
                                             work_items, attempts, annotations, deletion_tombstones, audit_log
                                           - pgmq queue `work` (send in same txn as work_items insert)
                                           - pg_cron: guarded 10 s tick -> pg_net -> Edge `worker`
                                           - Edge Functions: `admit` (validate+admit, 202/429/409),
                                             `worker` (90 s deadline, one provider call in flight),
                                             `sign` (ownership check -> short-lived signed URL), `export`
                                           - Storage: one private bucket (7-day images, 30-day manifests)
                                                     |
                                                     v
                                           CDSE Sentinel Hub (Catalog, Statistical, Process)
```

Moving parts: **3 vendors/accounts (Cloudflare, Supabase, CDSE) plus a Google Cloud project for OAuth**, **1 database**, **3-4 Edge functions**, **1 cron job**, **1 queue (inside the DB)**, **1 bucket**. No Redis, no second queue/orchestrator, no R2, no D1, no Workflows.

Why this meets each requirement at ₹0:
- **Durable jobs + retries:** `work_items` (domain state) + pgmq (lease, redelivery, attempt count, backoff via `set_vt`). Survives Edge restarts because state is in Postgres, not in a function.
- **Private storage:** Supabase private bucket, signed URLs minted by `sign` after an ownership check; short expiry (ARCH proposes 5 min).
- **Auth:** Supabase Auth with Google. No SMTP needed.
- **Free-tier fit:** 500 MB DB, 1 GB storage, 5 GB egress, 500k Edge calls, 50k MAU. Fits about 100 analyses/month (section 4).

Day-0 probes that can falsify this topology (do them before writing features):
1. Enable `pgmq` and `postgis` on a **Free** project; confirm Mumbai is selectable.
2. pg_cron + pg_net -> Edge `worker` with a 90 s run: does the invocation survive pg_net's 2 s default timeout, and does `EdgeRuntime.waitUntil` finish? (B7)
3. Google sign-in from a non-team account in "In production" with basic scopes only (B13).
4. Measure real Edge CPU for ingesting a 1-4 MiB PNG (stream to Storage) against the 2 CPU-s limit.
5. Confirm whether a cron-only project is kept alive (B3), or accept the daily ping.

Backup stance at ₹0: Free has no managed backups and Storage objects are never in backups. Keep ARCH s.8: a nightly `supabase db dump` taken by an accountable operator. Images are 7-day by design, so the DB dump is the only recoverable asset.

## 4. (b) Paid scale path, derived

### 4.1 Assumptions (explicit; every one is mine, none measured)

- FX: **₹96 per US$**. Source: x-rates monthly averages, Sep 2026 95.45, Oct 2026 (4 days) 95.95. https://www.x-rates.com/average/?from=USD&to=INR&amount=1&year=2026 . Indian GST (18%) is not included in the main figures; a separate column adds it (rate from general knowledge; Vercel's page confirms GST/VAT is added for billing addresses where applicable). Card forex fees not included.
- **Per-analysis call count** from ARCH s.7's own formula: calls = catalogue (1/section) + 3 quality + 1 render per section-window cell.
  - Site profile S: 1 section x 6 windows = 1 + 18 + 6 = **25 calls**; 6 frames.
  - Road profile R: 5 sections x ~4 windows = 20 cells -> 5 + 60 + 20 = **85 calls**; capped by the 25 MiB retained-evidence limit.
  - Blend 70% S / 30% R: **43 calls**, and **14.5 MiB** retained (S about 9.6 MiB at 1.6 MiB/frame, R at the 25 MiB cap).
  - 1.6 MiB per frame (about 1.5 MiB RGB PNG + a small quality PNG) is a guess; PNG of satellite imagery is poorly compressible. ARCH caps a response at 4 MiB. Measure it.
- Retention per ARCH: images 7 days, so resident evidence = created x 7/30.
- Each analysis's evidence is downloaded **3 times** in total (first view, revisit, export) = 43.5 MiB egress per analysis, assumed uncached (worst case; Smart-CDN cache hits are billed at the lower $0.03/GB cached rate).
- 2.5 analyses per active user per month (for MAU).
- DB rows about 0.1 MB per analysis (43 attempts x about 1.6 KB + observations), kept 30 days.
- Edge invocations: 15 per analysis (about 3 worker runs of about 20 provider calls each, plus admit, signed-URL and export calls).
- Provider calls take about 3 s each, serialized (one in flight, per ARCH). **Unmeasured.**
- CDSE/Sentinel Hub quotas and any imagery cost are **out of scope** (not hosting) and are likely to bind first; ARCH s.7 already says so.

### 4.2 Derived workload

| Monthly analyses | 100 | 1,000 | 10,000 |
|---|---|---|---|
| Provider calls (x43) | 4,300 | 43,000 | 430,000 |
| Serialized worker time (x129 s) | 3.6 h | 35.8 h | 358 h |
| Share of a 720 h month if evenly spread | 0.5% | 5% | **50%** |
| Evidence created (x14.5 MiB) | 1.4 GB | 14.2 GB | 142 GB |
| Resident evidence (x14.5 x 7/30 MiB) | 0.33 GB | 3.3 GB | 33 GB |
| Egress (x43.5 MiB) | 4.2 GB | 42 GB | 425 GB |
| Edge invocations (x15) | 1,500 | 15,000 | 150,000 |
| DB resident (x0.1 MB, 30 d) | 10 MB | 100 MB | 1 GB |
| Active users (÷2.5) | 40 | 400 | 4,000 |

Reading it:
- **Egress is the first Free wall:** 5 GB / 43.5 MiB = about **118 analyses/month**. With 5 GB cached egress as a separate pool the practical limit could roughly double (inference, depends on cache hits).
- **Storage is the second:** 1 GB / 3.38 MiB = about **300 analyses/month**.
- DB, MAU and Edge calls never bind in this range (500 MB, 50k MAU, 500k invocations). DB would first bind near 5,000 analyses/month on Free.
- **Throughput, not money, is the real scale limit:** at 10,000/month the single-flight worker is at 50% average utilisation and will queue for hours at peak. ### 5.2 DPDP Act 2023 / Rules 2025: what applies to storing user locations
Facts (sources in B21; Rule numbers per Mondaq/Khaitan summaries, not read from the Gazette):
- Rules notified **13 Nov 2025**. Notice, safeguards, breach, erasure, rights obligations (Rules 3, 5-16, 22-23) start **13 May 2027**; Consent Manager rules 13 Nov 2026. A shortened 12-month window was reported only for Significant Data Fiduciaries and not notified as of the sources found.
- **Rule 3 (notice):** itemised description of personal data and specified purposes, plain language, withdrawal link and complaint route.
- **Rule 6 (safeguards):** encryption/obfuscation/masking, access controls, **monitoring and logging, and retention of logs for breach detection for at least one year**, continuity measures (backups/availability).
- **Rule 7 (breach):** inform affected people "without delay"; detailed report to the Board within **72 hours**; no materiality threshold (per secondary sources).
- **Rule 8 (erasure):** erase when purpose ends or consent is withdrawn; the 3-year cap applies only to large e-commerce / social / gaming platforms, not to you.
- **Children:** under 18 needs verifiable parental consent (Rules, per Khaitan note).
- **Cross-border:** no blacklist notified; the Government "may restrict" transfers to specified countries. Localisation of traffic data for Significant Data Fiduciaries is a possible future rule.
- **Penalties** (secondary sources, DPDP Act schedule): up to **₹250 crore** for failing reasonable security safeguards (s.8(5)); up to **₹200 crore** for failing breach notification (s.8(6)).

Inference (not legal advice; no counsel consulted): a saved site polygon or corridor tied to a Google account is "personal data" because the account makes the person identifiable. That makes GeoVerify a Data Fiduciary and Supabase, Cloudflare and CDSE processors/recipients. The product is a small fiduciary, not a Significant one, so Rule 13 DPIA/audit does not apply at launch.

Design consequences (all cheap, all consistent with existing retention design):
1. **Consent notice at first login** (Rule 3 content): list data (Google email/name, polygons, dates, notes), purposes, retention (images 7 d, manifests/notes 30 d per ARCH), withdrawal and deletion route, grievance contact. Build before public launch; obligation date is May 2027 but it is cheaper now than retrofitting.
2. **Own audit log table** with 1-year retention, opaque IDs only (no polygon, no note text), because Supabase platform logs keep **1 day (Free) / 7 days (Pro)**. This **tension is real**: Rule 6 wants a year of logs; DPDP erasure wants personal data gone sooner. Resolve by logging IDs and actions only, never content.
3. **Erasure path** that also reaches backups: ARCH s.8 already requires a deletion tombstone ledger applied on restore. Keep it.
4. **Breach runbook**: who can be reached, where the 72-hour report goes. No code needed.
5. **18+ gate** in terms of service (Rules require verifiable parental consent for minors; a self-declaration gate is the cheapest mitigation, not a guarantee).
6. **Disclose the CDSE transfer:** polygons and dates are sent to the provider under *the app's* credentials, not the user's identity. Say so in the notice. Do not send email/name to the provider.
7. **Region:** Mumbai is not legally required today (no notified blacklist) but removes a future-restriction risk and is a plain-language selling point. Inference.

### 5.3 Google OAuth verification requirements
Fact (B13): scopes `openid`, `email`, `profile` only are non-sensitive -> **no full app verification**; brand verification only if you want app name/logo shown (takes "several business days"); production needs public homepage with privacy-policy link, verified domains, HTTPS redirects. Basic-scope apps are not subject to the 100-test-user cap or 7-day token expiry. Consequences: you need an **owned domain** (a `workers.dev` hostname cannot easily pass domain verification: inference, check), a **privacy policy page** (reuse the DPDP notice text), and to **publish the app to production**. Never request Drive/Photos/Maps scopes at launch: that triggers sensitive-scope verification (weeks) and is unnecessary.

## 7. Best recommendation and the strongest argument against it

**Recommendation:** Supabase (Mumbai) for auth, Postgres+PostGIS, pgmq, cron, Edge, private Storage; Cloudflare Worker with static assets for the frontend (plus optional keep-alive cron). ₹0 at about 100 analyses/month, $25 (₹2,400) at about 1,000, about $41 (₹3,900) at about 10,000. Defer R2. No extra orchestrator.

**Strongest argument against (steelman for all-Cloudflare):**
- Cloudflare Workflows *are* the durable-multi-step-with-retries primitive; you would write about 0 lines of claim/lease/fencing SQL. State persists across restarts, steps retry with backoff, sleeps up to a year, waiting costs nothing, no 150 s wall ceiling per step.
- Nothing pauses. Supabase Free pauses after a quiet week and has **no backups**; D1 gives **7-day Time Travel for free** (30 on Paid).
- Free caps are looser where it hurts: R2 10 GB with **zero egress** vs Supabase 1 GB with 5 GB egress. Your first wall (egress at about 118 analyses/month) simply does not exist on R2.
- One vendor, one bill, one dashboard, one deploy tool. Cost at 10,000 analyses/month is about **$5.5 vs $41-56**.
- No Edge 2 CPU-s limit; Paid Workers give 30 s of CPU per invocation by default, 5 min configurable.
- India edge presence and no region pinning to think about.

Why I still pick Supabase: Cloudflare gives you primitives but not auth. Google OAuth + sessions + token verification + RLS-equivalent authorisation + geometry validation (no PostGIS) are exactly where five students introduce vulnerabilities in a product that stores people's locations under a law with ₹250 crore ceilings. Supabase hands you those pre-built. The $20-35/month saving at scale buys back less than the expected cost of one authorisation bug.

**What would change my mind (concrete triggers):** (a) the Day-0 probes show pg_net -> Edge cannot reliably run 90 s units (B7), (b) Free-plan pausing or lack of pgmq/PostGIS blocks the ₹0 plan (B3, C1), (c) a prototype shows Workflow steps fit the 10 ms Free CPU limit *and* a vetted auth library (Better Auth) passes a security review, or (d) throughput becomes the constraint and Workflows' concurrency (100 free, 50,000 paid) is needed. If (a) or (b) happens, move orchestration to Cloudflare Workflows while keeping Supabase for Auth/DB/PostGIS only: a hybrid, not a rewrite.

### R2.2 Storage and egress: store pixels?
Decision: **store no rendered pixels on the server at launch.** Store manifest + geometry + annotations only. Thumbnails are re-rendered client-side from COG overviews and cached in the browser (Cache API/IndexedDB); a stored thumbnail saves little and costs rows.

Why this is safe, and its hole: pixels are re-derivable only while Element84 keeps the objects unchanged. A reprocessing exists already (`sentinel-2-c1-l2a` is a "Collection 1" namespace; processing baseline 05.13 is visible per item). If a source changes, the checksum mismatches and the manifest must show **"source changed since capture"**, not silently re-render. The durable snapshot is the user's **exported HTML** (embedded images), made at export time and held on their device. If server snapshots are wanted later, they are a Pro-tier feature priced by the original section-4 table (14.5 MiB per analysis).

Snapshots for exports on server / R2: **no.** Exports are generated and downloaded client-side, so nothing is hosted. R2 becomes right the moment you add **shareable report links**: a 10-20 MiB report viewed by many people is exactly the egress case where R2's zero egress beats Supabase's $0.09/GB. Add it then, not now.

### R2.3 Real scaling limit without a provider queue
In order of when it bites (not DB rows or MAU):
1. **Retention policy x Free DB size** (about 1,170/month at 12 months). A policy knob, and Pro removes it.
2. **Third-party public endpoints with unpublished limits.** Earth Search (no documented rate limit/SLA found), the S3 buckets (AWS Open Data sponsored), CelesTrak (documented per-IP limits). Because calls originate from user browsers, load is spread across user IPs (a scaling plus), but **carrier-grade NAT, campus and office IPs concentrate many Indian users behind one IP** (inference), which can trigger per-IP throttling. Probe with a realistic multi-user burst.
3. **Per-user client cost:** windowed COG reads from us-west-2 (S3 buckets have no CDN; CloudFront fronts only the STAC API), JS TIFF decode and memory on low-end phones. This is latency/UX per user, not system capacity. Unmeasured.
4. Supabase Auth MAU (about 125k analyses/month on Free, 250k on Pro) and Edge calls are far away.
The single-flight worker ceiling (358 h/month at 10k, section 4.2) **disappears**.

### R2.4 What the new model breaks, and the fixes
- **DPDP audit logging (Rule 6, 1-year logs).** No server code sits in the read path, so reads are not application-logged. Fix: AFTER triggers on writes to `investigations`/`manifests`/`annotations` write `audit_log` (actor `auth.uid()`, op, row ID, time; no content). For logins, prefer a Supabase Auth Hook if available on Free (UNVERIFIED), else `auth.audit_log_entries` (UNVERIFIED that hosted projects populate it), else a client-asserted `session_start` RPC (weaker). `pgaudit` may exist as an extension (UNVERIFIED). Own table because platform logs keep 1 day/7 days.
- **New DPDP/privacy exposure (this is the big one).** Previously the app's service account hid user identity from the provider. Now the **user's IP and AOI-derived requests go straight to Element84/AWS (US) and CelesTrak**. STAC searches reveal the bbox; COG range requests reveal the pixel window at about 10 m precision. A proxy cannot fully hide the second without server mediation. Decision: query STAC with a **coarsened bbox (MGRS tile or about 10 km snap)**, crop client-side, and **disclose** third-party reads in the Rule 3 notice. Cross-border transfer is not restricted today (no notified blacklist). Do not promise location privacy from AWS.
- **Abuse/rate limiting of anonymous use.** Anonymous = no backend, so nothing server-side to abuse or pay for. Abuse surfaces that remain: (a) logged-in accounts filling the Free DB: cap by DB trigger (rows/day, total, geometry size); (b) auth endpoints are IP-rate-limited by default (30 per 5 min; anonymous 30/hour) and Turnstile is available; (c) `/api/tle`: Cloudflare Free allows 1 rate rule (10 s windows), enough; (d) PostgREST with a stolen anon key is bounded by RLS and the row caps. Load on third-party public endpoints is **not** yours to throttle server-side; mitigate by client-side caching and polite request patterns.
- **Offline export.** Breaks if export reads from the manifest alone: it would need live COGs. Fix: export **embeds the rendered PNGs at export time** (data URIs, about +33% size: about 19 MiB for a 14.5 MiB set), so it works offline and survives source reprocessing. Memory pressure on phones is real for road analyses; cap frames per export, offer per-section export. Re-opening an old saved investigation online re-renders from COGs and flags checksum drift.
- **Evidence integrity.** Client-computed hashes are forgeable by the client. What keeps this "evidence" and not a screenshot: server-set `created_at`, DB-enforced immutability of frozen manifests, STAC `file:checksum` of each source, and the optional `verify` spot-check. State this limit plainly in the product copy.

### R2.5 Revised verdict and strongest counter
Pick stands and gets stronger: Supabase Auth + Postgres + one Worker, **$0 to about 1,100 analyses/month, then $25 flat**. All-Cloudflare no longer wins on orchestration (there is none); it would still need hand-built auth.

Strongest argument against: **go local-first with no backend** (IndexedDB + exported JSON/HTML). Then no personal data is held, DPDP drops to near zero, cost is ₹0 forever, and there is nothing to pause or back up. What you lose is exactly what makes it a product: cross-device continuity, a **server timestamp and immutability** that distinguish evidence from a screenshot, and any shared audit trail. Choose Supabase if those matter; if the first tester only wants a report file, ship local-first and add Supabase when someone asks for sync.

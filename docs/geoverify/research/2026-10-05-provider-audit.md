# GeoVerify provider and hosting revalidation — 2026-10-05

Status: fresh documentation audit and architectural recommendation; no account, live processing, deployment or capacity validation. Access date for every source below: **2026-10-05**. Existing GeoVerify documents supplied the claim inventory, not the evidence. This audit uses current primary provider documentation and unauthenticated capability reads.

## Recommendation

For the first bounded public evidence workbench, prefer a **probe of CDSE Sentinel Hub Catalog + Statistical + synchronous Process APIs, behind short Supabase Edge Functions**, with Supabase Auth/Postgres/private Storage and a static React/Vite/Leaflet frontend. Keep openEO batch as the documented alternative if the synchronous route fails its provenance, quality, latency or resource gates. This remains the user's selected **B managed processing + C evidence workbench** direction.

The reason is operational simplicity: the current month-one product needs dated observations, quality information, comparison and user notes. Those do not inherently need a long-running remote batch job. Provider-rendered images can avoid live Python/GDAL hosting and the remote create/start/poll/cancel/result-ingest lifecycle. This is an architectural inference, **not measured superiority**. It does not remove durable frame records, atomic claims, request deduplication, quota reservations, recovery or retention.

## Three architecture variants

| Variant | Advantages | Costs and risks | Recommendation |
| --- | --- | --- | --- |
| **1. Progressive managed observations**: Catalog → candidate quality statistics → one Process rendering per accepted actual observation; short Edge work units and Postgres state | Keeps the selected B+C product, removes a live Python service and long remote-job lifecycle; produces first evidence without waiting for every frame; no server raster decoder needed | Exact acquisition agreement across Catalog/statistics/rendering must be proven. Many small requests consume account request limits. Edge CPU/wall/byte limits, multipart parsing, retention and queue recovery still need testing | **Preferred month-one probe**, conditional on the gates below |
| **2. Managed openEO batch workbench**: Python/openEO client, durable job controller, provider outputs, private evidence storage | Better suited to broad temporal/raster graphs and future validated analysis; provider can perform heavier computation | Experimental M2M setup/linkage; uncertain credit consumption; job lifecycle and ambiguous submissions; ingest/provenance handling; sleeping runtime complicates control | Keep as **alternative when Variant 1 cannot meet evidence or workload requirements**. Do not build both live paths in month one |
| **3. STAC/COG local or browser computation**: public catalog and windowed data reads | Less dependence on one managed raster API; direct inspectability; can support later reproducibility investigations | CORS, data transfer, block decompression, projection, masks and browser device limits; server fallback needs compute; geometry sent to external data hosts; own processing responsibility | **Future experiment**, not silent replacement of B+C and not the month-one release dependency |

Avoid choosing Sentinel Hub's separate synchronous **openEO-over-Sentinel-Hub** endpoint merely for naming consistency: its current documentation describes a beta with a single temporal slice even when a longer extent is supplied. It is not evidence of complete time-series support. [Synchronous openEO endpoint](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/OpenEO.html)

## Implementation changes that reduce work without weakening evidence

1. **Make observation cells the work unit.** One cell identifies a site or road section, requested bin, selected acquisition, rendering policy and quality policy. Before/after views reference these same cells. No duplicated provider call for the same retained cell.
2. **Use provider statistics for quality summaries.** Prefer bounded SCL/data-mask statistics instead of loading GeoTIFFs into Edge. This is a proposed route, not a validated metric. Define the whole-AOI denominator explicitly; excluding clouds first and measuring only surviving pixels would misstate coverage. Enforce acquisition agreement between statistics and rendered evidence. Never equate SCL quality filtering with proof of a cloud-free scene.
3. **Return partial results honestly.** A frame can be ready while another remains pending or unavailable. Keep requested dates, observed dates, quality reasons and gaps visible. Cache exact observations; do not manufacture images for empty bins.
4. **Retain the small reliability core.** Store immutable request fingerprint, owner, attempts, reservations and frame status. Atomically claim each work unit and finish with a version check. Bound retries and account for possibly consumed quota when an HTTP outcome is unknown. Provider cancellation/inventory reconciliation from openEO is unnecessary for a synchronous response path, but internal leases and recovery remain necessary.
5. **Use a provider adapter only at the evidence boundary.** `search`, `quality`, `render`, normalized provenance and measured consumption are enough initially. No speculative multi-provider orchestration framework or automatic paid fallback.
6. **Separate ephemeral evidence from durable author notes.** A disclosed short-lived private image cache and self-contained export can meet a pilot's needs; user notes still need backup/restore. Do not promise permanent evidence history while operating within a one-gigabyte free store. Retention clocks, deletion handling and backup scope must be concrete before launch.
7. **Do not make backups into a second application.** Choose and test one bounded export/restore procedure appropriate to the stated retention promise. Export actual retained objects when promising their recovery. Keep a deletion record that prevents older snapshots from restoring removed user data. A permanent archive or formal 24-hour RPO is a separate unproven commitment, not a free-tier feature.

## Hard probes before selecting Variant 1 for public use

| Probe | Required evidence |
| --- | --- |
| Account and eligibility | Server OAuth credentials work for Catalog, Statistical and Process on the chosen CDSE account; record actual shared allowances and applicable terms. No duplicate accounts to multiply free quota. No account or credential creation performed during this audit. |
| Acquisition identity | Catalog-selected acquisition, statistics input and Process `userdata` agree. A multi-tile observation records all contributing inputs. Same-day duplicate/reprocessed products cannot silently substitute. Fail closed on mismatch. |
| Quality and grid | Cloud/shadow/nodata handling, native SCL resolution, resampling, common preview grid and AOI denominator are demonstrated on cloudy, clear, boundary-crossing and road-section cases. No construction verdict depends on unvalidated thresholds. |
| Runtime and bytes | Measure end-to-end one-unit p95 latency, CPU, memory and total bytes, including token reuse, metadata parsing, multipart boundaries, Storage upload and DB writes. Proposed 90-second processing deadline and 4 MiB response cap are application policies, not published provider guarantees; reject oversize or late results safely. |
| Response formats | Prove the exact chosen output bundle. Provider PNG plus metadata is insufficient if mask/quality provenance cannot be recovered. Do not assume a multi-output HTTP response is automatically supported by the chosen Edge parser. |
| Failure and quotas | Exercise 401/403/429/5XX, malformed responses, cloud-only windows, lost HTTP responses, repeated browser submission, worker termination and storage/DB failures. Successful provider work followed by application failure must not cause unrestricted repeat charges. |
| Scheduled progress | Show pending cells resume after the browser closes and after runtime restart. Verify the selected managed scheduler, claim expiry and cleanup behavior. A scheduled trigger alone is not proof of eventual completion or no inactivity pausing. |
| Metering | Measure full site and road timelines, including rejected candidate statistics, Catalog pagination, retries and evidence downloads. Reserve bounded request/PU/storage/egress budgets before admission. Published monthly limits are not a concurrent-customer capacity estimate. |
| Identity/privacy/export | Non-team OAuth sign-in, owner isolation, private images, sanitised notes, credential-free logs and a self-contained image/provenance export work. An expiring URL is not export content. |
| Restore/delete | Restore both metadata and any promised retained images, reapply post-snapshot deletions, and verify objects cannot reappear under a different key. Record actual observed recovery time, with no unsupported SLA. |

## Claims this audit cannot establish

- A GeoVerify account will receive a particular quota, support decision or billing behavior.
- A representative 12-bin/road-section workload fits free capacity, Edge limits or a chosen turnaround target.
- A `budget` field is a provider-enforced spending cap, or a timed-out request consumed no quota.
- Documentation-listed source metadata equals complete per-pixel lineage for the chosen processing script.
- Commercial eligibility of every future dataset, third-party layer, basemap or premium API.
- Construction detection accuracy, completion status, calibrated confidence, road-length or area measurement quality.
- Permanent availability, funded free tiers, SLA, demand, reachable testers, or customer willingness to pay.

The account and live probes remain unperformed. These gaps should be tracked as explicit release conditions rather than filled with optimistic numbers.

# GeoVerify four-week delivery and validation checkpoints

Date: 1 October 2026. Status: draft planning contract for the selected **B + C** route: managed imagery processing with a user evidence workbench. No application, experiment, deployment, customer interview, benchmark result, or release approval is recorded here.

Read with [PRD](PRD.md), [TRD](TRD.md), [How it works](HOW_IT_WORKS.md), and [Design](DESIGN.md). Product scope belongs in the PRD; processing, records, and recovery contracts belong in the TRD; this document states the evidence and decisions needed at each checkpoint. Record actual work and deviations in [LOGBOOK](LOGBOOK.md), retaining research and assumptions in [KNOWLEDGE_DUMP](KNOWLEDGE_DUMP.md).

## Delivery boundary and dependencies

Confirmed scope: a commercial product, free initially; both large buildings/sites and roads/highway corridors; before/after inspection and a multi-date timeline; free/open imagery, with resolution allowed to vary. The target is one month, initially ₹0 cash spending, with paid hosting when free services cannot meet requirements. India-first is a planning assumption. No customer segment, reachable tester, demand evidence, team capacity, exact start date, or later paid amount is established. Optional claim checking remains conditional on usefulness.

The month-one target is a **bounded public live pilot** accepting new user geometry and date windows. A static demonstration of precomputed examples is a useful interim checkpoint; it does not fulfil this target. A live dated-imagery workbench can pass independently of automatic detection. User annotations must identify their author and evidence; they are interpretations, not independent truth or calibrated model confidence.

Provisional operating caps for resource probes: sites up to 1 km²; roads up to 10 km with a full corridor width up to 200 m and area up to 2 km²; up to 12 windows within 24 months; one active provider job per account. These are candidate workload limits, not validated feature-size or accuracy guarantees. Revise them after measured jobs; retain both asset classes and timeline support.

Dependencies are: commercially suitable provider access and a usable balance for the actual backend identity; representative scene availability; recoverable application state and retained outputs; bounded submissions; usable geometry/date/provenance contracts; and named people to execute the plan. Construction attribution and measurements additionally require independent references and a locked evaluation. If a dependency fails, record a hold and a specific next action. The deadline does not waive it.

Suggested responsibilities are product/recruitment, imagery/reference review, backend/provider/recovery, and interface/reporting. These are work streams, not four assumed team members. One person can execute them sequentially; assign names and capacity on Day 1. Independent reference review requires another reviewer or documented external assessment; a sole author comparing their own annotations cannot establish independence.

The live-workbench critical path is access/balance → representative observations → asynchronous processing and durable records → both-asset inspection/timeline → recovery, retention, and bounded-public checks → release review. Reference collection and recruitment run in parallel. References → calibration → blind evaluation form a separate critical path for automatic layers. Additional staffing can parallelise interface and provider work after shared input/output contracts are settled; it cannot remove independent-review or provider dependencies.

## Exploratory reference and evaluation protocol

The fuller discovery proposal was 36 independent projects. **If developing/evaluating an automatic layer this month, target 24 projects**, 12 per asset, to exercise the protocol. Independently documented cases also help evaluate user interpretation without requiring detector calibration. Within each asset seek four construction-change, four stable, and four non-construction-change cases. Allocate 12 development, six calibration and six untouched challenge projects for an automatic method, balanced where possible. The tiny calibration/challenge sets contain only one example per category per asset; estimates will be unstable. These are research targets, not adequate release thresholds or proof that 24 cases are attainable.

If independent references cannot reach this target, retain the documented cases and limitations, continue the evidence-workbench pathway, and keep unsupported automatic claims disabled. Do not drop roads or timelines to make the sample appear complete. Expand to a separately designed test set when error costs, desired precision, geography, and population are known. The presentation's 40–60 sites and 75% verdict target remain source proposals, not achieved or approved criteria.

Build the register before viewing predictions. Cover different footprint shapes/areas, road widths, material contrast, neighbourhoods, regions, seasons, imagery sampling, and quality. Include agriculture, flooding, vegetation changes, demolition, shadows, cloudy windows, and missing observations. All dates, image patches, nearby sections, and shared developments of a project stay in one group and partition. Training/development, threshold calibration, and final testing serve different purposes. Repeatedly inspecting the blind set converts it into development data; obtain a new blind set for subsequent claims.

For each reference, retain geometry, dated source/provenance, usage rights, observable milestone, generic change, construction subtype, measurement where supportable, uncertainty, reviewer identities, and adjudication. Seek independently dated photographs, orthophotos, or engineering inspections. A permit/announcement alone does not establish visible geometry or physical completion. Two reviewers label blind to predictions; record disagreements and unknowns. Product-user annotations and analyst descriptions using the same product imagery cannot be silently recycled as independent labels. This protocol follows independent-reference and uncertainty principles in [Olofsson et al.](https://doi.org/10.1016/j.rse.2014.02.015); grouped/spatial separation follows [Roberts et al.](https://doi.org/10.1111/ecog.02881).

Report buildings and roads separately. For generic change, use changed-class precision, recall, F1/IoU, project false alarms/misses, and coverage. Construction-specific classification needs a separate confusion matrix against construction/confounder labels. Area outputs need referenced footprint/change-area overlap, signed bias, absolute m² error, and relative error when the denominator is nonzero; never call changed area floor area. Road outputs need referenced corridor/centreline overlap with stated positional tolerance, missed/spurious sections, absolute metres and relative length error; connectivity is a separate promise. Summarise uncertainty at the project/group level. Millions of pixels do not provide millions of independent test projects.

Record actual observation dates and composite support windows. A milestone absent at the last clear date and present at the next is bounded between those observations; missing earlier/later evidence gives a one-sided bound. Show gaps and interval width, and evaluate milestone ordering, interval compatibility, and false events. Broad compatible intervals may be unhelpful. Do not interpolate completion percentages or infer abandonment from a flat curve or missing imagery.

For illustration, a hypothetical 75% result has approximate 95% Wilson intervals of 60–86% for 30/40 independent tests and 63–84% for 45/60; partitioning those projects across assets/classes weakens precision further. This arithmetic is not a GeoVerify result and does not repair biased sampling. [NIST Wilson method](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm)

## Feature and release gates

All gates are pending. Calibration selects operating thresholds; release policy decides whether evidence, error costs, and coverage justify exposing a feature. No numeric accuracy promise or calibrated confidence claim is adopted.

| Gate | Pass evidence | Hold/action |
|---|---|---|
| Access and ₹0 operation | Actual backend identity authenticates; intended commercial use and a usable allowance are established; bounded workload fits without unintended spending. | Resolve identity/credits/terms or propose the paid transition with a concrete amount. |
| Live evidence workbench | New inputs for both assets produce dated inspection and timeline, clear quality/no-data/gap states, provenance, retained annotations/reports, and effective workload/access controls. | Repair failed system checks; a static demo remains interim. |
| Generic-change overlay | Independently labelled evaluation, documented calibration, frozen settings, tested quality gate, and explicit experimental wording support the public policy. | Keep overlays disabled or internal. Clear imagery alone is insufficient evaluation. |
| Automatic construction attribution | Independent construction/confounder labels and held-out evidence support the exact feature and supported conditions, with an agreed error/coverage policy. | Display authored interpretation separately; omit automatic construction claims. |
| Area/road measurements | Independent geometry and per-asset measurement tests support stated units, uncertainty, and dimensions. | Omit quantities; provide inspectable imagery/annotations. |
| Claim checking | Testers find the step useful; the exact observable claim has validated evidence criteria. | Keep optional or omit it. Never certify whole-project completion, cost use, or acceptance from optical evidence. |
| Runtime, recovery, retention | Representative cold/repeated jobs and failures retain consistent state, retrieve results, honour retention, and consume measured resources within caps/reserve. | Reduce workload or move to suitable hosting/storage before live launch. |
| Customer usefulness | A real target user completes a relevant task and identifies a repeatable decision, usable evidence, and reason to return. | Record demand as unvalidated even if the technical pilot launches. |

## Resource and failure evidence

Measure provider and application behaviour separately. A provider job marked finished does not prove a saved report exists; an application timeout does not prove provider work stopped. Retain identifiers and reconcile actual status after interruption. Probe create/start/status/cancel/delete, failed/running jobs, duplicate submission, download retries, result expiry, local restart, and retrieval from durable application storage. Never claim an unexecuted probe passed.

Require cancellation to reach a terminal provider state; test a lost create response before retrying to avoid duplicate charges. Verify any provider budget parameter's enforcement before treating it as a spending cap. CDSE's documented seven-day signed result links and 90-day completed-result retention are different limits. Copy rasters and root/child/source metadata into application storage, verify checksums/retrieval, and test export/restore of both records and objects. Confirm actual scene IDs, acquisition dates, and matching site-valid fractions rather than relying only on aggregate temporal ranges. [Result metadata](https://documentation.dataspace.copernicus.eu/APIs/openEO/openeo-backend/docs/job-result-stac11.html), [retention change](https://dataspace.copernicus.eu/news/2025-5-6-important-change-retention-period-openeo-job-results), [job options](https://documentation.dataspace.copernicus.eu/APIs/openEO/job_config.html)

CDSE documents experimental service-account authentication with separate job/result identity and credit balance. Linking personal credits requires support; successful authentication alone does not prove the account's advertised allowance is usable by the backend. Check the actual identity/balance first. Published quotas and concurrency are provider constraints that can change; the one-active-job cap is GeoVerify's proposed policy. [Client credentials](https://documentation.dataspace.copernicus.eu/APIs/openEO/authentication/client_credentials.html), [quotas](https://documentation.dataspace.copernicus.eu/Quotas.html)

Probe sign-in and report access from a non-team pilot user. If Supabase is selected, default SMTP's restrictions must not be mistaken for public email authentication capacity; confirm the selected login path before inviting users. [Authentication SMTP limits](https://supabase.com/docs/guides/auth/auth-smtp)

Probe dated preview exports as well as analytical rasters. Native PNG capability does not establish a PNG for every date: select/reduce one observation explicitly and verify multi-output filenames/source provenance. Confirm display projection/bounds and identical colour stretch. Test diagonal road bounding boxes, per-frame dimensions and sequential ingest/conversion memory, not only selected area. Also test the shared nonterminal queue cap, before-admission `429`, idempotent reservations, and a missing selected comparison bin. Verify report retention clocks start at publication and restore applies a current deletion ledger covering post-snapshot deletions before any user access.

Capture queue, processing, download, and report time separately for cold and repeated requests at candidate caps, including multiple windows and both assets. Record credits per job/failed attempt/retry, transferred bytes, peak application resources, retained bytes, quota failures, recovery time, and human review minutes. Compare the forecast workload plus a recorded reserve with actual available credits/storage. Agree turnaround and retention objectives from these measurements; neither “under ten minutes” nor a monthly capacity total is established.

## Customer assignment and unsent outreach

The product/recruitment owner should prepare six prospective contacts: three building/site owners or civil engineers and three road/corridor engineers or monitoring teams. Seek three short discovery sessions, ideally spanning both assets. These are recruitment targets, not interviews already arranged. The human owner chooses contacts and sends the invitation; **no messages have been sent**.

Draft invitation: “We are testing a free tool for comparing dated satellite observations of large sites and road corridors. Could you spend 20 minutes showing how you currently check changes and trying one comparison? We would like to learn what evidence helps your decision and where imagery is insufficient. The prototype does not certify construction completion.”

Assign a task using a known site and relevant period: confirm geometry, locate dates/gaps, inspect change, annotate a finding, and explain the next real-world decision. Ask what they use now, what the report misses, whether they would repeat the task, and what warrants payment. Observe completion, time, misunderstandings, corrections, and commitment to a second task. Positive comments, traffic, or a classmate's demonstration alone do not establish buying demand.

## Experiment and resource record templates

**Experiment record:** ID/date/owner; question and feature; hypothesis; project IDs and partition; reference sources/reviewers; input geometry/windows; provider/collection/scene IDs; method/settings/version; quality exclusions and reasons; outputs/provenance; per-asset metrics and uncertainty; coverage; annotation/reference distinction; failures/confounders; decision; next action. Record unsuccessful and interrupted attempts.

**Resource record:** run/job IDs and backend identity; workload area/route width/length/windows/bands; actual allowance before/after; queue/processing/download/report time; credits and retries; transferred/retained bytes; memory/runtime observations; retention/expiry/retrieval result; recovery/quota/cancellation result; human minutes; estimated repeated workload and reserve; proposed caps; pass/hold owner. Never store secrets in either record.

## Scaling trigger and action matrix

| Measured trigger | Next action and evidence required |
|---|---|
| Expected bounded jobs plus reserve exceed actual credits | Reduce frequency/windows/caps, schedule intake, or price a provider allowance; confirm backend identity and spend before activation. |
| Queue or turnaround exceeds the agreed objective | Locate provider/transfer/interface bottleneck; alter scheduling or capacity only after measured benefit. |
| Sleep/restarts or ephemeral storage break recovery/history | Use durable job/report/object storage and a suitable runtime; repeat recovery/retention checks before migrating users. |
| Retained bytes or egress approach the chosen allowance | Review retention/preview sizes and storage plan; preserve report provenance and user expectations. |
| Public misuse consumes the available allowance | Tighten request limits, admission controls, and per-user budgets; verify them against representative misuse. |
| Users repeatedly need corrections or scene selection | Prioritise workbench interaction and measure review time/agreement; corrections remain authored evidence. |
| A recurring confounder defeats an automatic layer | Obtain labels, test a simpler correction or alternative, and repeat independent evaluation before adding models. |
| Roads or sites below supported spatial detail recur | Explain insufficient evidence; evaluate suitable free/open observations. Model complexity does not create observed detail. |
| New regions/seasons/assets are requested | Collect external references and test transfer; expand supported claims only where evidence permits. |
| Repeat users need collaboration/private history | Validate the workflow and retention/access needs before adding organisational features. |
| Free hosting cannot satisfy live gates | Present a measured paid hosting/storage plan with an explicit budget; user-authorised paid transition is not an unspecified purchase. |

Day 20 must identify the enabled feature set, unmet gates, measured caps, resource reserve, responsible owner, and next review. The present state is a planning package: every execution and release gate remains untested.
